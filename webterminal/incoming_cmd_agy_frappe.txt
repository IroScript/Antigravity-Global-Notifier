READ EVERYTHING BEFORE MAKING ANY CHANGE.

==================================================
PRIMARY GOAL
==================================================

Build a two-VM architecture in which the production environment reproduces
the CURRENT WORKING LOCAL FRAPPE ENVIRONMENT AS EXACTLY AS PRACTICALLY POSSIBLE.

The local environment is the authoritative runtime reference.

DO NOT casually install "latest".
DO NOT upgrade Frappe.
DO NOT upgrade ERPNext.
DO NOT upgrade the custom app.
DO NOT substitute package versions merely because newer versions exist.

The production environment must use the SAME tested versions/revisions as local.

Architecture:

VM-1 = APPLICATION VM
VM-2 = DATABASE VM

VM-1 must contain:

- Frappe Bench
- exact local Frappe revision
- exact local ERPNext revision
- exact local Alco Ecommerce revision
- Python environment
- Redis services required by Frappe
- Frappe web processes
- workers
- scheduler
- Nginx / supported production web layer
- Node/Yarn/build tools only as required by this exact Frappe version
- application assets

VM-2 must contain:

- MariaDB Server
- database storage
- MariaDB native service management
- no Frappe application runtime unless an official technical dependency proves
  it is actually required

VM-1 must connect to VM-2 over the private network.

MariaDB port 3306 MUST NOT be exposed publicly.

==================================================
ABSOLUTE RULE: LOCAL IS THE VERSION SOURCE OF TRUTH
==================================================

Before installing ANYTHING on either VM, audit the existing LOCAL working
Frappe environment.

Do not infer versions from branch names such as:

version-16
develop
main

A branch name is NOT sufficient.

Capture the exact state.

For every installed app capture at least:

1. app name
2. app path
3. git remote
4. current branch
5. exact HEAD commit SHA
6. git status
7. whether tracked files are modified
8. whether untracked files exist
9. app version exposed by Frappe/Bench
10. whether the local commit exists on the configured remote

At minimum inspect:

- frappe
- erpnext
- alco_ecommerce
- every other app installed on the actual site

Use evidence such as:

git rev-parse HEAD
git status --short
git remote -v
git branch --show-current

and appropriate Bench/Frappe commands.

DO NOT claim parity using only a human-readable version such as 16.x.x.

Exact commit SHA is required whenever the app is Git-managed.

==================================================
LOCAL DOCUMENTATION RULE
==================================================

The machine already contains local Frappe documentation/source documentation.

Locate it first.

Determine whether that documentation corresponds to the SAME locally installed
Frappe revision/version.

If yes:

LOCAL VERSION-MATCHED FRAPPE DOCUMENTATION IS THE PRIMARY DOCUMENTATION SOURCE.

Use official online Frappe/MariaDB documentation only:

- when local documentation does not cover something,
- to validate behaviour,
- or to confirm installation/deployment requirements.

Never silently replace version-specific local instructions with instructions
from a different/latest Frappe version.

Document:

LOCAL DOC PATH
LOCAL FRAPPE SHA
DOC VERSION/REVISION IF DETERMINABLE
MATCH VERDICT = PASS / FAIL / UNKNOWN

Do NOT copy documentation to production merely for the sake of runtime parity.

Documentation itself is not a runtime dependency.

==================================================
DO NOT BLINDLY COPY THE LOCAL BENCH
==================================================

"HUBOHU LOCAL → VM" means FUNCTIONAL AND VERSION PARITY.

It does NOT mean blindly rsync/copying:

- Python virtualenv
- node_modules
- compiled native libraries
- cache
- logs
- sockets
- PID files
- Redis runtime state
- temporary files

Those can be machine/OS specific.

Instead reproduce them correctly from the captured versions and dependency
definitions.

The following MUST be preserved/reproduced:

- exact Frappe commit
- exact ERPNext commit
- exact custom app commit
- all legitimate custom source files
- DocType definitions
- hooks
- fixtures
- patches
- frontend source
- application configuration shape
- required Python dependencies
- required Node/Yarn dependencies
- customizations required by the site
- database schema/data as required for the requested deployment
- exact installed-app relationship

If local contains uncommitted changes, STOP THE NORMAL DEPLOYMENT PATH.

Do not discard them.

Report exactly:

- repository
- modified files
- untracked files
- diff summary

Determine whether those changes are intentional source code that must first be
made reproducible/version-controlled.

Never silently deploy a different state.

==================================================
PHASE 2 — PARITY DESIGN
==================================================

Before installing anything, create:

TARGET_PARITY_PLAN.md

It must map:

LOCAL COMPONENT                TARGET COMPONENT
----------------------------------------------------------
Frappe SHA             -> VM-1 same SHA
ERPNext SHA            -> VM-1 same SHA
Alco SHA               -> VM-1 same SHA
Python version         -> VM-1 compatible/same version
Node version           -> VM-1 compatible/same version
Yarn version           -> VM-1 compatible/same version
MariaDB version        -> VM-2 same compatible version
Redis requirements     -> VM-1
Workers                -> VM-1
Scheduler              -> VM-1
Nginx                  -> VM-1
Database               -> VM-2

For every difference between local and target, explicitly state:

- difference
- reason
- impact
- whether parity is still valid

A difference cannot be silently accepted.

==================================================
PHASE 3 — VM-2 DATABASE SERVER
==================================================

Prepare VM-2 first.

Install ONLY the required MariaDB server stack and operating-system dependencies.

Prefer the exact locally tested MariaDB version when supported by the target OS.

If exact binary/version parity is impossible:

STOP and report the incompatibility before substituting another version.

Configure MariaDB for remote access ONLY through the VM private network.

Create the required database/user privileges for the Frappe site.

Do not expose MariaDB to:

0.0.0.0/0
public Internet
arbitrary hosts

Restrict database network access to VM-1 private IP/network.

Verify:

- mariadb.service is running
- boot enablement
- active restart policy
- listening address
- port
- firewall/security rules
- authentication
- private connectivity

Inspect, do not assume:

systemctl status mariadb
systemctl show mariadb.service -p Restart -p RestartSec
systemctl cat mariadb.service

Do NOT invent custom restart daemons if native MariaDB/systemd behaviour is
sufficient.

Document actual state.

==================================================
PHASE 4 — VM-1 APPLICATION SERVER
==================================================

Install the OS/runtime prerequisites appropriate for the EXACT Frappe version
captured locally.

Do not use "latest Frappe installation" instructions unless they exactly match
the local version.

Create the Bench.

Fetch Frappe at the exact captured commit.

Fetch ERPNext at the exact captured commit.

Fetch Alco Ecommerce at the exact captured commit.

For example, conceptually:

clone repository
checkout EXACT_SHA
verify HEAD == EXPECTED_SHA

Do this for every app.

Never finish with:

"version 16 matched"

The PASS condition is:

EXPECTED_SHA == ACTUAL_SHA

for every Git-managed application.

==================================================
PHASE 5 — CONNECT FRAPPE TO VM-2
==================================================

Configure the Frappe site so the database host is VM-2's PRIVATE address.

Use Frappe-supported database configuration keys.

Conceptually:

db_host = <VM2_PRIVATE_IP>
db_port = 3306

Use the actual credentials securely.

Do not commit passwords to Git.

Verify from VM-1:

- VM-2 resolves/reaches
- TCP 3306 is reachable privately
- authenticated MariaDB connection works
- Frappe can connect

Do not declare PASS merely because port 3306 responds.

Authenticated DB access must succeed.

==================================================
PHASE 6 — DATABASE / SITE TRANSFER STRATEGY
==================================================

Determine the requested production data source.

There are TWO different things:

A. SOFTWARE PARITY
B. SITE DATA PARITY

Do not confuse them.

Software parity means:

same Frappe
same ERPNext
same Alco
same source/configuration logic

Data parity means:

same site database/files/private files/public files as a selected source.

If the intention is to reproduce the existing local site exactly, then use a
proper Frappe-supported backup/restore procedure rather than manually copying
MariaDB data directories.

Preserve:

- database
- public files
- private files
- site configuration as appropriate

Secrets must be handled securely.

If this is instead a fresh production site, create a fresh site against VM-2
and install the same apps in the same required order.

Do not decide silently between FRESH SITE and CLONED SITE.

Infer it only if existing requirements make it unambiguous; otherwise report
the choice before destructive execution.

==================================================
PHASE 7 — MIGRATION / SCHEMA FITTING
==================================================

Once the exact application code is in VM-1 and the site uses VM-2:

run the appropriate Frappe migration for the target site.

The important architecture is:

VM-1:
Frappe migration code executes

VM-2:
MariaDB schema/data receives the database changes

Verify:

- migration completes
- installed app list is correct
- DocTypes sync
- custom fields/customizations sync
- patches complete
- fixtures sync
- no pending migration error

Do not claim database parity just because the website opens.

Do not install extra frontend libraries unless they exist in the local working
